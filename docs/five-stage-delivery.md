# ForgeOS 五阶段产品化交付基线

状态：实施中
产品主线：`codex/enterprise-platform-phase-4`
集成分支：`codex/project-platform-five-stage`

## 产品目标

ForgeOS 是以项目为一级对象的企业 AI 原生应用开发、发布与运维平台。OpenAI Codex
负责持续开发会话、模型交互与工具执行；ForgeOS 负责项目身份、工程上下文、验证证据、
版本治理、部署控制、审计和恢复。浏览器只呈现网关权威状态，不充当工程数据或执行证据的
可信来源。

## 阶段一：正式产品主线与真实项目闭环

验收条件：

- GitHub 默认分支指向 ForgeOS 产品线，并启用必要检查与禁止强推保护；
- `projectId` 是不可变主键，项目显示名称和 URL 不再承担身份职责；
- 项目、根目录、Git 仓库和长期对话绑定由网关持久化；
- 跨项目移动、解绑、归档不会遗留旧标签、最近对话或兼容映射；
- `.forgeos/project.json` 由网关原子维护，可用于重启恢复与冲突预览；
- 旧项目迁移失败不会污染 Registry，也不会移动或删除源码和 Codex 历史。

## 阶段二：统一项目工作台

验收条件：

- 项目中心、AI 开发、代码、验证、发布、运维和审计共享同一个 `projectId` 上下文；
- 一个项目可拥有多条长期 Codex 对话，刷新后恢复最近对话；
- 重命名后深链接仍能恢复同一项目；Windows 路径不区分大小写，POSIX 路径保持大小写语义；
- 生命周期、验证和工程证据以网关为权威，不因网络或权限错误降级为浏览器本地真相；
- 文件、Git、Diff、终端、验证、发布和运维作为按需二级工作面，不复制 Codex Runtime。

## 阶段三：发布与部署闭环

验收条件：

- 验证绑定项目根目录、Git commit、操作者、退出码、有界日志和证据摘要；
- 验证命令超时、取消或等待异常时只执行有界的尽力清理，不把终止工具成功或直接进程退出误报为完整
  进程树已停止；输出管道未在截止前关闭同样进入持久化项目隔离，网关重启不会自动解锁，只有负责人
  确认外部清理后才能通过受审计操作恢复；
- 制品由服务端计算 SHA-256、签名、存储，并在下载前重新验证；
- 发布必须绑定现存目标环境，生产发布执行配置化审批门禁；
- 部署只能引用同项目、已发布且目标环境一致的 Release；
- `projectId` 是生命周期、制品、发布、部署与审计的唯一寻址键；仍使用 `projectName` 的旧客户端会收到
  `409 UPGRADE_REQUIRED`，必须刷新 Project Registry V2 后重试，避免重命名或同名项目造成越权绑定；
- 部署和健康检查由网关执行并记录服务端证据，浏览器不能自报成功；
- 失败、回滚和审批事件进入项目审计与通知路由。

## 阶段四：企业控制能力

验收条件：

- owner、admin、viewer 的读取和变更权限在 HTTP 与 WebSocket 保持一致；
- 专用 owner 模式强制所有者门禁，默认单管理员模式保持可操作；
- 审批按操作者凭据与角色去重，不能通过重复提交伪造多人审批；
- viewer 无法读取敏感生命周期命令、部署日志、上传内容或下载项目制品；只允许读取脱敏状态和验证签名；
- 外部部署只保存非敏感引用，凭据由运行环境或企业流水线管理；
- 通知 Webhook 执行 HTTPS、地址范围、DNS 解析和允许主机约束；
- 项目审计以 `projectId` 为目标，记录操作者、动作、结果和恢复事件。

## 阶段五：稳定发布与运维恢复

验收条件：

- Linux、macOS、Windows 构建矩阵产出网关包；标签只有在同一 commit 已通过产品分支 `push` CI 后
  才能创建永久 GitHub Release，PyPI 可选；
- Windows 升级包校验平台、清单和摘要；替换网关必须通过 `/readyz` 与实例健康校验；
- 新网关退出或超时自动恢复前一 Release，活动指针损坏可从备份恢复；
- ForgeOS 自管 profile 数据支持带清单和逐文件 SHA-256 的备份、校验和原子恢复；
- 恢复前自动生成 pre-restore 备份，损坏、越界路径或不兼容版本必须拒绝；
- CI 覆盖 Registry、迁移、生命周期策略、升级回滚、前端状态与真实浏览器项目流程；
- Windows 操作员包必须离线安装并真实调用安装后的 `forgeos` 命令入口，不以源码目录脚本代替；
- 至少使用一个真实代码库完成持续开发、验证、构建与审计试点。

## 发布判定

只有代码评审、要求的自动化检查和远端 CI 全部通过，且所有已知限制被明确记录时，才可
把集成分支标记为候选版本。测试环境缺失不等同于通过；本地无法编译的 Rust 测试必须由
Windows MSVC 与 Linux CI 补充验证。

## 已知限制与后续加固（P2）

- 项目 Registry 与 `.forgeos/project.json` 已提供请求级回滚，但尚未使用跨文件、跨 profile、
  跨网关进程的持久化事务日志；同一路径不得由多个网关实例或 profile 并发创建项目。后续应
  增加按规范根路径的进程级锁与启动恢复日志。
- 数据恢复以 profile 目录和审计文件为原子单元，并保留可验证的 pre-restore 备份；跨卷、
  多单元替换期间若主机崩溃，当前版本仍需操作员依据 pre-restore 备份恢复。后续应增加恢复
  journal 和启动时的 staging/rollback 自动判定。
- 网关包内层清单固定并验证原生二进制摘要；静态资源的发行方真实性仍以外层 ZIP SHA-256
  和 GitHub provenance attestation 为信任边界。安装前必须先验证这两项，后续再将静态资源
  Merkle/文件清单纳入内层签名。
- owner/admin 审批按已认证凭据与角色去重，不等价于企业人员身份、组织成员或双人职责分离。
  接入企业 IdP 前，不应把同一操作者持有两组凭据解释为独立审批人。
- Project Lifecycle ID Consolidation 之后，审计列表只按不可变 `projectId` 查询。升级前仅以
  项目显示名称写入、且没有稳定项目标识的历史记录不会自动猜测归属，以避免同名项目之间的
  审计数据泄漏；后续应通过带冲突预览和回滚能力的显式迁移工具补录关联。
- viewer 只允许读取脱敏生命周期状态并验证制品签名，不能下载制品字节。这是企业模式的有意
  安全收紧，与早期网关允许只读账号下载的行为不兼容；需要下载制品的操作员应使用 owner 或
  admin 凭据，并在升级后刷新旧客户端。
- 五阶段共享改动超过单次理想评审规模；合并前应按“项目身份与迁移”“生命周期权威执行”
  “升级、备份与恢复”拆分为可独立回滚和验证的提交/PR。
